# 規格書：LINE 快速比價機器人 v1（2026 年底版）

Status: ready-for-agent
Created: 2026-09-26
Deadline: 2026-12-31
Supersedes: 舊版 PROJECT_SPEC.md（動漫周邊 / FB 網址 / Netlify 版本）

## Problem Statement

台灣的網路購物者想買一樣東西時，同一件商品在蝦皮、momo、PChome、露天、日本樂天、Mercari、淘寶等平台的價格差異可能很大，但要逐一打開每個平台、用正確的關鍵字搜尋、再判斷搜到的是不是同一件商品，既費時又需要經驗。一般人常用的是縮寫或慣用語（例如「AJ1」「排少」「趴娃」），在平台上直接搜常搜不到或搜錯；看到二手、配件、不同世代的商品混在結果裡，也很難判斷「真正的合理價格」是多少。結果就是資訊落差：懂門路的人買得便宜，一般人付了不必要的溢價。

## Solution

一個免安裝的 LINE 聊天機器人。使用者只要傳一段文字（可以是口語、縮寫、慣用語）或一張商品照片，機器人會：

1. 用 AI 理解使用者真正想找的商品，並判斷商品類別；
2. 依類別自動挑選最適合的 6 個購物平台，同時查詢；
3. 用 AI 過濾掉不是同一件商品的結果（配件、不同型號、不同規格）；
4. 在 15 秒內回覆一張比價卡片：各平台的真實價格（依價格排序）、可讓使用者自己核對的前幾筆商品與連結、以及價格更新時間；來不及查到價格的平台仍提供搜尋連結。

排序只依價格，不受任何分潤關係影響。

## User Stories

### 輸入與理解
1. 身為網購者，我想直接傳一段文字給機器人，就能開始比價，這樣我不用安裝任何 App。
2. 身為網購者，我想用平常習慣的縮寫或慣用語（例如「AJ1」「switch2」）搜尋，這樣我不必先查正式商品名稱。
3. 身為網購者，我想傳一張商品照片給機器人，這樣我不知道商品名稱時也能比價。
4. 身為網購者，我想傳一段夾雜售價與雜訊的賣場文字（例如「售 XX 全新未拆 1500」），機器人能抓出商品本體，這樣我可以直接轉貼看到的貼文內容。
5. 身為網購者，當我的描述太模糊、無法辨識時，我想收到明確的提示告訴我該補充什麼，而不是收到錯的比價結果。
6. 身為網購者，當我傳的內容跟購物無關時，我想收到禮貌的說明，這樣我知道機器人能做什麼。

### 平台選擇
7. 身為網購者，我想讓機器人依商品類別自動挑出最相關的 6 個平台，這樣我不用自己決定去哪裡查。
8. 身為 3C 家電買家，我想看到 PChome、momo、蝦皮、Yahoo 購物、露天、日本樂天的價格，因為這些是 3C 的主要通路。
9. 身為美妝保養買家，我想看到 momo、蝦皮、PChome、Yahoo 購物、日本樂天、淘寶的價格。
10. 身為服飾鞋包買家，我想看到蝦皮、momo、淘寶、露天、Mercari、日本樂天的價格。
11. 身為動漫周邊/玩具買家，我想看到 Mercari、日本 Yahoo 拍賣、日本樂天、蝦皮、露天、淘寶的價格，這樣我可以比較日本原價與台灣轉售價。
12. 身為運動戶外用品買家，我想看到 momo、PChome、蝦皮、Yahoo 購物、日本樂天、淘寶的價格。
13. 身為網購者，當機器人判斷不出類別時，我仍想看到一組通用平台（蝦皮、momo、PChome、Yahoo 購物、露天、淘寶）的價格。

### 比價結果
14. 身為網購者，我想看到每個平台「與我要的商品相符」的最低價，這樣我知道哪裡最便宜。
15. 身為網購者，我想讓平台依價格由低到高排列，這樣我一眼就知道最佳選擇。
16. 身為網購者，我想看到每個平台最便宜的前幾筆商品標題與連結，這樣我能自己確認 AI 比對的是不是同一件東西。
17. 身為網購者，我想看到海外平台價格已換算成新台幣，這樣我能直接比較。
18. 身為網購者，我想看到價格的更新時間，這樣我知道資料新不新。
19. 身為網購者，我想點卡片上的按鈕直接跳到該平台的搜尋結果，這樣我能馬上購買。
20. 身為網購者，當某平台查不到或太慢時，我仍想看到該平台的搜尋連結，這樣我可以自己去看。
21. 身為網購者，我想讓配件、二手零件、不同世代或不同規格（容量、尺寸）的商品被排除在價格計算外，這樣最低價才有意義。
22. 身為網購者，我想知道機器人用什麼關鍵字幫我搜尋，這樣結果不對時我能換個說法再試。

### 速度與可靠性
23. 身為網購者，我想在 15 秒內一定收到回覆，這樣我不會以為機器人壞了。
24. 身為網購者，我想在等待時看到「處理中」的動畫，這樣我知道機器人有在動。
25. 身為網購者，當有人剛查過同一件商品時，我想幾乎立即拿到結果。
26. 身為網購者，當 AI 服務暫時忙碌或故障時，我想收到清楚的說明與替代的搜尋連結，而不是沒有回應。
27. 身為網購者，我不想因為網路重送而收到兩張重複的卡片。
28. 身為網購者，我想在任何時段（包括深夜第一個使用）都能正常得到回覆。

### 公平與揭露
29. 身為網購者，我想確定排序只依價格，不會因為平台有分潤而被排到前面，這樣我能信任結果。
30. 身為網購者，我想能查看免責聲明與平台比較說明，這樣我知道價格僅供參考、以及有哪些潛在費用（運費、代購費）。
31. 身為網購者，我想知道海外價格的換算方式（匯率與海外交易手續費），這樣我理解數字怎麼來的。

### 引導與輔助（Rich Menu）
32. 身為新使用者，我想在加入好友時收到使用說明，這樣我知道怎麼開始。
33. 身為網購者，我想從選單打開新手指南，這樣我能學會怎麼傳訊息最準。
34. 身為海外購物新手，我想從選單看到集運倉介紹，這樣我知道怎麼把日本商品寄回台灣。
35. 身為網購者，我想從選單回報錯誤或建議，這樣我遇到比錯價的情況能反映。

### 防濫用
36. 身為服務營運者，我想限制每位使用者每分鐘最多 5 次查詢，這樣少數人無法耗盡資源。
37. 身為服務營運者，我想只處理通過 LINE 簽章驗證的請求，這樣別人無法偽造訊息。

### 營運者（開發者本人）
38. 身為營運者，我想新增或調整某類別的 6 個平台時只改一張對照表，這樣維護成本低。
39. 身為營運者，我想新增一個購物平台時只需要實作一個統一介面的轉接器，這樣擴充平台不會牽動其他程式。
40. 身為營運者，我想讓付費的第三方 API 只在評測實驗中啟用，這樣正式服務維持零額外成本。
41. 身為營運者，我想確保系統永遠不會顯示寫死的假價格，這樣不會誤導使用者。
42. 身為營運者，我想從日誌看到每次查詢各平台花了多久、成功或失敗，這樣能找出拖慢的平台。
43. 身為營運者，我想讓服務在 Render 免費方案上穩定運行，並靠外部排程防止休眠。
44. 身為營運者，我想申請各平台的聯盟行銷，讓購買連結帶有分潤參數，這樣服務有潛在收入來源。

### 研究評估
45. 身為研究者，我想用一套 50 筆的評測集自動跑比價流程，這樣能量化產品是否達標。
46. 身為研究者，我想量到「15 秒內回覆的比例」，這樣能驗證速度目標。
47. 身為研究者，我想量到「平均取得幾個平台的真實價格」，這樣能驗證 6 平台覆蓋目標。
48. 身為研究者，我想量到「AI 過濾後比對正確的比例」（同型號、同規格即正確，顏色不計），這樣能驗證比價是否可信。
49. 身為研究者，我想讓評測結果按類別、文字/圖片分開統計，這樣能找出最弱的環節。
50. 身為研究者，我想讓評測走的流程與使用者實際使用的流程完全一致，這樣評測數字才有代表性。
51. 身為研究者，我想對 10–20 位受試者做前後測問卷與 SUS 可用性量表，這樣能評估機器人是否真的降低資訊落差。

## Implementation Decisions

### 架構
- **部署**：Render 常駐 web service（免費方案），由外部 cron-job 每 10 分鐘呼叫健康檢查端點防止休眠。Netlify 相關設定與 serverless 入口為遺留物，予以移除。
- **Webhook 處理順序**：驗證簽章後立即回應 LINE 200，比價在背景執行，完成後用 reply token 回覆。不使用 push message（避免消耗官方帳號訊息額度）。
- **單一狀態存放**：快取與限流維持在程式記憶體中（單一常駐實例即可正確運作）；重新部署或重啟後清空為可接受行為。
- **預熱**：啟動時預熱熱門關鍵字的機制保留（常駐實例下會正常執行），預熱清單改為通用購物的熱門商品。

### 模組

1. **比價流程（新，主要深模組）**
   - 單一入口：輸入為「文字」或「圖片」（二擇一），輸出為結構化的「比價結果」，不含任何 LINE 格式。
   - 內部依序：AI 解析 → 類別判定 → 查對照表取 6 平台 → 並行查詢所有平台 → AI 相符性過濾 → 排序 → 組成結果。
   - 以依賴注入接收：AI 解析器、平台轉接器集合、時鐘、快取。以便測試替換與評測共用。
   - **時間預算**：整體硬上限 15 秒（自收到訊息起算）。平台查詢在上限內盡量等待全部 6 個；時間到即以當下已取得的結果組成回覆，未完成者標記為「僅提供連結」。
   - 比價結果的形狀（概念）：
     - 使用者原始輸入、AI 理解後的商品名稱（中文）與搜尋關鍵字（各語言）
     - 類別
     - 每個平台一筆：平台名稱、狀態（有價格 / 查無相符 / 逾時 / 失敗）、相符商品的最低價（TWD）、原幣別價格、前幾筆可核對商品（標題、價格、連結）、平台搜尋連結（含分潤參數）
     - 依價格排序後的平台順序
     - 價格取得時間
     - 是否來自快取

2. **AI 解析器（修改既有）**
   - 所有文字與圖片輸入一律經過 Gemini，移除「純英數型號略過 LLM」的捷徑，確保縮寫、慣用語能被展開。
   - 輸出新增「商品類別」欄位，值限定為六類之一：3C 家電、美妝保養、服飾鞋包、動漫周邊/玩具、運動戶外、其他。
   - 移除「動漫周邊專用」的假設與欄位語意，改為通用商品描述；保留售價抽取（使用者貼賣場文字時可比較）。
   - 單次解析時間上限約 3 秒；重試需計入整體 15 秒預算，不得無上限重試。
   - 使用已購買的 Gemini 額度；模型名稱由環境變數設定。

3. **類別→平台對照表（新）**
   - 一份靜態、可人工編輯的設定，一類對應 6 個平台（見 User Stories 8–13）。
   - 程式不得由 LLM 自由決定平台。
   - 候選平台池：蝦皮、momo、PChome、Yahoo 購物/拍賣、露天、日本樂天、Mercari、日本 Yahoo 拍賣、淘寶。

4. **平台轉接器（統一介面，重構既有＋新增）**
   - 介面：給定關鍵字與逾時 → 回傳商品清單（標題、價格、幣別、連結、可選縮圖）；失敗時回傳明確的失敗狀態而非拋出未處理例外。
   - 資料來源優先順序：官方 API ／ 聯盟行銷 API → 網頁爬取備援。付費第三方 API（RapidAPI）僅在評測設定下啟用，正式服務關閉。
   - 既有平台（Mercari/Buyee、日本樂天、日本 Yahoo 拍賣、蝦皮、淘寶、台灣 Yahoo）重構為此介面。
   - 新增平台依序：PChome → momo → 露天 → Yahoo 購物。各平台的可用 API／爬取方式需在實作前查證。
   - 刪除所有產生假價格（mock plausible price）的程式路徑。

5. **相符性過濾（新／擴充既有 AI 判斷）**
   - 對每個平台回傳的商品清單，判斷哪些與使用者要的商品「同型號、同規格」；顏色差異不排除。
   - 排除配件、零件、不同世代、不同容量/尺寸。
   - 平台最低價只從相符商品中計算；無相符商品時狀態為「查無相符」。
   - 過濾耗時計入 15 秒預算；可採批次一次呼叫處理全部平台的結果以節省時間。

6. **定價換算（沿用既有）**
   - 海外價格換算 TWD：匯率 × 價格 ＋ 1.5% 海外交易手續費；極端低價與離群值剔除邏輯沿用。
   - 不再計算「到岸成本」與「溢價警示」作為主要輸出（屬舊動漫轉售情境）。

7. **LINE 卡片產生器（修改既有）**
   - 輸入改為「比價結果」，只負責呈現。
   - 呈現：商品名稱與搜尋關鍵字、依價格排序的 6 平台列（價格或「查看」連結）、可核對的前幾筆商品、價格更新時間、分潤連結按鈕。
   - 排序完全依比價結果，卡片產生器不得因分潤重新排序。

8. **快取（沿用既有）**
   - 以正規化後的查詢為鍵，保存比價結果 1 小時。
   - 卡片顯示的是原始取得時間，而非快取命中時間。

9. **限流（沿用既有）**
   - 每位使用者每 60 秒最多 5 次查詢。

10. **評測程式（新）**
    - 讀取評測集檔案（50 筆；六類平均約 8 筆；約 70% 文字、30% 圖片；每筆含正確商品名稱與型號規格、至少一個正確商品連結）。
    - 以真實轉接器呼叫比價流程入口（與正式服務同一入口），記錄每筆的耗時、各平台狀態、相符判斷。
    - 產出三項指標：15 秒內回覆比例、平均取得真實價格的平台數、比對正確率；並依類別與輸入型態分組。
    - 可選擇啟用付費 API 做對照實驗。

### 營運
- 聯盟行銷：申請蝦皮、momo 等平台聯盟計畫；分潤參數只影響連結，不影響排序。
- 日誌：每次查詢記錄各平台耗時與狀態、是否快取命中、AI 解析耗時。
- 負載：先以 Render 免費方案運行；第 8 週評測時一併做壓力測試，不足時再決定是否升級。

## Testing Decisions

### 好測試的原則
- 只測外部行為（輸入 → 可觀察的輸出），不測內部函式名稱、呼叫順序或私有細節。
- 不替換被測模組內部的函式；只在明確的切入點替換外部依賴（AI、平台、LINE API、時鐘）。
- 時間相關行為（15 秒截止、1 小時快取）用可控制的假時鐘測，不真的等待。

### 三個測試切入點
1. **比價流程入口（主要）**
   - 替換：假 AI 解析器（回傳指定的類別與關鍵字）、假平台轉接器（可設定回傳內容、延遲、失敗）、假時鐘。
   - 驗證：依類別選出正確的 6 個平台；「其他」類的預設平台；15 秒截止時已完成者有價格、未完成者為僅連結；排序只依價格；分潤不影響排序；不相符商品被排除；全數不相符時為「查無相符」；平台失敗不影響其他平台；快取命中與 1 小時過期；結果中的價格取得時間；永遠不出現假價格。
   - 評測程式也從此入口執行（換成真實轉接器）。
2. **LINE webhook（既有）**
   - 替換：整個比價流程、LINE API。
   - 驗證：簽章錯誤回 400；合法請求立即回 200 且比價在背景進行；Rich Menu 指令回覆；限流訊息；AI 故障時的降級訊息；比價結果被正確轉成卡片並以 reply token 回覆；不重複回覆。
3. **平台轉接器（統一介面）**
   - 替換：以錄下的真實平台回應（HTML/JSON 檔）取代網路。
   - 驗證：每個平台正確解析出標題、價格、幣別、連結；空結果；被擋或格式異常時回傳失敗狀態。

### 前例
- 既有 webhook 測試以 TestClient 對 webhook 端點送出簽章請求，為切入點 2 的前例。
- 既有輕量抓價與爬蟲測試以固定 HTML 內容驗證解析，為切入點 3 的前例。
- 既有整合測試直接替換主程式內部函式，屬本規格要淘汰的寫法，將改接到切入點 1 或 2。
- 現況：2026-09-26 於專案虛擬環境執行，既有 143 個測試全數通過。

## Out of Scope

- 分享 Facebook 貼文網址並自動擷取貼文內容（列為未來方向）。
- 到岸成本計算（運費、代購費）與「溢價過高」警示作為主要功能。
- 依分潤高低排序或推薦特定平台。
- 使用者帳號、查詢紀錄、價格追蹤／降價通知。
- 網頁版或 App 版介面。
- 多實例部署、外部資料庫或外部快取服務。
- 付費第三方 API 用於正式服務。
- 候選平台池以外的平台（例如 Amazon、酷澎）。
